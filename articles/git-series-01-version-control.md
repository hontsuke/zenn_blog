# 「最新版」フォルダが増殖していませんか？――変更履歴管理の話

昔から、ファイルをいじる前にはバックアップを取る癖があります。

大きな変更をする前に、とりあえずフォルダごとコピーする。

名前はこんな感じ。

```text
project
project_backup
project_backup_20260927
```

もう少し慎重になると、

```text
project_old
project_old2
project_最新版
project_最新版2
project_本当に最新版
```

みたいなことになってきます。

笑い話みたいですが、似たようなことをやった経験がある人は結構いるんじゃないでしょうか。

別にこれが悪いわけではありません。

変更前の状態を残しておけば、何か失敗したときに戻せます。

ちゃんと役に立つ方法です。

ただ、ファイルが増えてくると、だんだん別の問題が出てきます。

## どれが本物だ？

しばらく経ってから、そのフォルダを開きます。

すると、

```text
project
project_backup
project_backup_20260920
project_backup_20260925
project_backup_20260927
```

と並んでいる。

さて。

**今使っているのはどれでしょう。**

日付を見れば、なんとなく分かります。

たぶん一番新しいやつ。

でも、9月27日のフォルダは「変更してみたけど失敗したので使わなかったもの」かもしれません。

実際に使っているのは25日の方かもしれない。

さらに困るのが、

**「何を変えたんだっけ？」**

です。

ファイルを一つずつ比較すれば分かります。

でも面倒です。

数日前なら覚えているかもしれません。

半年後なら、たぶん覚えていません。

## バックアップと変更履歴は、似ているけど違う

フォルダをコピーして残しておく方法は、バックアップとしては機能します。

その時点の状態を丸ごと保存しているからです。

でも、

「いつ」

「何を」

「なぜ」

変更したのか。

そこまでは残りません。

つまり、

**状態を保存することと、変更の履歴を管理することは別の話です。**

これ、プログラムに限りません。

文章を書いていても起きます。

```text
企画書.docx
企画書_修正版.docx
企画書_修正版2.docx
企画書_最終版.docx
企画書_最終版2.docx
企画書_本当の最終版.docx
```

「最終版2」の時点で最終じゃないだろ、という話ですが、こういうファイル名には妙なリアリティがあります。

## 実は、人間が手作業で履歴管理している

日付を付けてフォルダをコピーする。

変更前のファイルを別名で残しておく。

これは言ってみれば、

**変更履歴を人間が手作業で管理している状態**

です。

だったら、その部分をコンピュータにやらせればいい。

変更したファイルを全部コピーして残すのではなく、

「この時点ではこうだった」

「ここを変更した」

「この変更にはこういう意味があった」

という履歴を残す。

必要になったら、以前の状態との差を見る。

場合によっては、以前の状態へ戻す。

そういうことをするための仕組みがあります。

それが**バージョン管理**です。

## Gitの話をする前に

バージョン管理というと、今ならGitの名前がまず出てくると思います。

でも、この記事でいきなり

```bash
git init
git add .
git commit
```

とはやりません。

コマンドを覚える前に、

**そもそも何のためにGitなんてものを使うのか**

を考えてみたいからです。

Gitを使わなくても、フォルダをコピーすればバックアップはできます。

一人で作っているなら、それで十分なこともあります。

それなのに、なぜわざわざGitを使うのか。

自分がこのことを強く意識するようになったのは、以前働いていた職場で使われていたバージョン管理システムがきっかけでした。

そこで使われていたのはGitではありません。

**Subversion（SVN）でした。**
