## 一人で使うなら、ブランチなんて要らない？

前回まで、Gitが変更の履歴を管理する仕組みだという話をしてきました。

前回の最後に、次は「ブランチ」の話をすると書きました。

Gitを使い始めると、かなり早い段階で出会う言葉です。

でも、最初はこれがよく分かりません。

特に一人で開発していると、

**「別にmainにそのままコミットしていけばいいんじゃないの？」**

と思います。

実際、小さな修正ならそれでもできます。

自分しか触らない。

誰かと同時に作業するわけでもない。

変更したらコミットして、問題があれば戻せばいい。

それなのに、なぜわざわざブランチを作るのでしょう。

## 今の正しい状態と、これから試す変更を分けたい

ブランチが欲しくなる理由を、自分はこう考えています。

**今からやる変更を、今の正しい状態から分離したい。**

たとえば、今ちゃんと動いている状態が `main` にあるとします。

ここに新しい機能を追加したい。

作り始めてみたら、一発で完成するとは限りません。

途中まで作った。

まだ動かない。

テストも通らない。

やっぱり設計を変えたい。

昨日の状態に戻したい。

そういうことは普通にあります。

その作業途中の状態を、今までちゃんと動いていた状態と混ぜたくありません。

そこで枝を一本作ります。

```text
o---o---o  main
         \
          o---o---o  feature
```

`main` は、今まで動いていた状態のまま。

新しい変更は、別の枝で進める。

うまくいったら、最後にmainへ戻す。

```text
o---o---o-----------o  main
         \         /
          o---o---o  feature
```

これがブランチの基本的な使い方です。

もちろん、実際の履歴はもっと複雑になります。

でも最初は、

**「作業中」と「今の正しい状態」を分けるもの**

くらいに考えておけばいいと思います。

## ブランチは、画面で見た方が分かりやすい

前回、Gitを操作する入口はいろいろある、と書きました。

コマンドでも操作できます。

たとえばブランチを作ることも、切り替えることも、コマンドでできます。

でも、自分はブランチについては、画面で見た方が理解しやすいと思っています。

たとえばSourcetreeで履歴を見ると、

「ここまではmain」

「ここから別のブランチに分かれた」

「そこで何回かコミットした」

「最後にmainへ戻ってきた」

という流れが、線として見えます。

GitLabなどでも、コミットやブランチの流れをグラフで見ることができます。

文字で、

「ブランチとは履歴から分岐した……」

と説明されるより、

**枝分かれして、最後に戻ってくる線を見る方が早い。**

少なくとも自分はそうでした。

## 昔、職場ではSourcetreeを使ってもらっていた

前回、

> Sourcetreeそのものが、Gitだと思っていた人がいました。

という話を書きました。

それでも、自分がGitを説明するときにSourcetreeを使っていたのには理由があります。

Gitの構造が、比較的見えやすかったからです。

どのブランチにいるのか。

どこから分かれたのか。

どのコミットがどこにあるのか。

どこでマージされたのか。

コマンドを覚えていなくても、画面を見ながら説明できます。

自分がやりたかったのは、Gitのコマンドを暗記してもらうことではありませんでした。

**今、自分がどこにいて、何を変更しようとしているのか。**

そこを分かってほしかったのです。

## TortoiseGitではダメだったのか

Windowsでバージョン管理を使っていた人なら、TortoiseSVNを使ったことがある人もいると思います。

エクスプローラー上で右クリックすると、コミットや更新などの操作が出てくる。

自分も使っていました。

そしてGitには、よく似た操作感のTortoiseGitがあります。

SVNからGitへ移る人にとっては、これはかなり入りやすいと思います。

今まで使っていたのと似た画面から操作できる。

覚え直すことが少ない。

これは明確な利点です。

ただ、自分が人にGitを説明するときには、Sourcetreeの方を選びました。

理由は、

**Gitの構造そのものが見えやすかったから。**

TortoiseGitが悪いという話ではありません。

右クリックから必要な操作をする、という使い方は便利です。

ただ、その便利さの裏側で、

「今どのブランチにいるのか」

「ローカルとリモートはどういう関係なのか」

「履歴がどこで枝分かれしているのか」

といったものが、自分には少し見えにくく感じました。

SVNから来た人にとって使いやすいことと、Gitの考え方を理解しやすいことは、必ずしも同じではありません。

自分は後者を優先したかった。

だからSourcetreeを使いました。

## 一人でもブランチを使う理由

ここまで読むと、

「でも、それって複数人で開発するときの話じゃないの？」

と思うかもしれません。

もちろん、複数人で開発するとブランチはさらに重要になります。

Aさんは新機能を作る。

Bさんはバグを直す。

同時にmainを書き換えていたら大変です。

だから作業を分ける。

これは分かりやすい使い方です。

でも、一人でも同じです。

今日の自分は、新機能を作っている。

途中で、昨日公開した部分にバグが見つかった。

新機能はまだ完成していない。

でもバグだけは先に直したい。

そんなとき、作業がブランチに分かれていれば、

**作りかけの新機能を抱えたまま、別の変更を始められます。**

```text
          o-------o  fix
         /         \
o---o---o-----------o-------o  main
         \                 /
          o---o---o---o---o  feature
```

「一人だからブランチはいらない」ではありません。

一人でも、同時に扱いたい変更が一つとは限らないのです。

## コマンドは、全部は覚えていない

Gitの説明を読んでいると、どうしてもコマンドの話が多くなります。

ブランチを作るコマンド。

切り替えるコマンド。

マージするコマンド。

間違えたときに戻すコマンド。

さらに少し進むと、`rebase` や `cherry-pick` なんて言葉も出てきます。

このあたりから、

「Git、やっぱり難しいな」

となりやすい。

自分もコマンドを全部覚えているわけではありません。

特に、たまにしか使わない操作は忘れます。

`cherry-pick` したい。

何をしたいかは分かっている。

でも、途中で競合したときの続行は何だったっけ。

中止するには何だったっけ。

そういうのを毎回覚えておくのは面倒です。

昔なら検索していました。

今ならAIに聞きます。

というより、

**AIにやらせます。**

> ここから作業用のブランチを作って。

> このコミットだけ、こっちのブランチに持ってきて。

> 競合したので、状態を確認して。

それで済む場面が増えました。

## コマンドを覚える重要性は、少し下がった

これは、Gitを学ばなくてよくなった、という話ではありません。

むしろ逆かもしれません。

AIがコマンドを実行してくれるようになると、人間が全部のコマンドを暗記する必要性は下がります。

でも、

**何をしたいのかは、人間が分かっていないといけません。**

今のmainは残したい。

ここから別の変更を始めたい。

この変更だけ取り込みたい。

この作業はまだmainに入れたくない。

そこが分かっていれば、

「どういうGitコマンドを打てばいい？」

はAIに聞けます。

逆に、

「何がどうなっているのか分からないけど、なんとかして」

では、AIが操作できても、その結果が自分の望んだ状態なのか判断できません。

だからAI時代には、

**Gitのコマンドを覚えることより、Gitで何をしたいのかを理解することの方が重要になった。**

自分はそう感じています。

## ところが、そのAI自身が変更を始めた

ここまでは、

「人間がやりたいことを決めて、AIにGitを操作してもらう」

という話でした。

ところが最近は、それだけではなくなっています。

AI自身がコードを書きます。

ファイルを変更します。

テストをします。

コミットまでします。

しかも、一つのAIだけとは限りません。

自分が変更する。

別のAIにも変更させる。

また別のAIにレビューさせる。

一人で開発しているはずなのに、

**コードを変更する主体が、一人ではなくなってきました。**

そうなると、

「一人で作っているんだから、mainに直接入れていけばいい」

という話も、少し変わってきます。

最近、自分がこの連載を書いている環境でも、まさにそれが起きました。

作業中の記事。レビュー中の記事。公開していい記事。

一人でやっているのに、だんだん複数人開発のような管理が必要になってきました。

次は、

**AI時代の個人開発で、ブランチやGit Flowをどう考えるか。**

実際に今この連載でやっていることも含めて、考えてみます。
