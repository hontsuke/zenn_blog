## TDDが実務で割に合わない、というよくある話

TDD（テスト駆動開発）が良いものだというのは、たぶん誰も否定しません。それでも実務でなかなか定着しないのは、単純に工数の問題です。テストを書くコストと実装するコストを両方払った上で、その効果を説明できないと、見積もりの段階で削られてしまう。理屈は正しいのに、コストが割に合わない、というやつです。

個人開発でも似たようなことは起きていて、「一人だし別にテストなくても自分が把握してればいいか」で済ませてしまいがちでした。

## 「AI駆動ならコストが消えるはず」という仮説

最近は実装をほぼ Claude Code に任せているのですが、ここでふと思ったのが「テストを書くのも実装するのも AI がやるなら、人間が払っていた工数コストがまるごと消えるのでは」という話でした。

しかも AI は自信満々に、それっぽいけど的外れなコードを書いてしまうことがあります。テストが先に落ちることを確認してから実装させる、という TDD の縛りは、まさにこの失敗パターンに直接効きそうです。

というわけで、[Superpowers](https://github.com/obra/superpowers) という Claude Code 用のプラグインを導入してみました。red-green-refactor の TDD サイクルを強制したり、実装前にブレインストーミング・計画のフェーズを挟んだり、サブエージェントに実装させて別のエージェントにレビューさせたりする、開発手法をまるごとプラグイン化したようなものです。

## 実際使ってみたら、コストは消えずに形を変えただけだった

しばらく使ってみての結論ですが、コストは消えていません。**人間が払っていた時間コストが、そのままトークン消費というコストに置き換わっただけ**でした。

テストを書く工程、テストが失敗することを確認する工程、実装する工程、レビューする工程。どの工程も律儀にこなしてくれるのは間違いないのですが、その分だけ会話のやり取りも実行時間も増えます。「サクッと直したい」くらいの軽微な修正でも、TDDのフルコースを律儀に回されると、地味にトークンを消費している感覚があります。

理屈の上では「AIなら工数コストが消える」と思っていたのですが、実態は「人間の時間という通貨で払っていたものを、トークンという通貨で払うようになった」だけでした。

## それでも使い続けている理由

コストが形を変えただけなら割に合わないのでは、と思われるかもしれませんが、それでも使い続けています。理由は2つあります。

**1. 品質担保**

これは素直な理由です。テストが先にあることで、AIが実装を変な方向に持っていったときに気づきやすくなります。「動いてるように見えるけど実は壊れている」を検出しやすくなるのは、実装を丸ごと任せている以上、単純にありがたいです。加えて、Superpowersのレビュー工程がかなり強いのも大きいです。実装した本人とは別の文脈のサブエージェントが見てくれるので、自分では気づけなかった見落としを拾ってもらえる場面が何度もありました。

**2. 属人化しなくなる**

個人開発なので属人化もクソもないだろう、と思っていたのですが、実際には別の意味で効いてきました。

AI には会話をまたいだ記憶がありません。今日 Claude Code に実装してもらった内容を、数ヶ月後にまた別の会話で触ってもらうとき、AI はゼロからコードを読み直すことになります。人間である自分自身も、数ヶ月前に何を意図してこの実装にしたか、正直そこまで覚えていません。

そんなときにテストがあると、「このコードが何を保証すべきか」がコードそのものに明文化されて残ります。記憶にも、その場限りの会話の文脈にも依存しない仕様書として機能してくれるわけです。これは、普段の開発以上に「記憶を持たない存在に実装を任せている」個人開発のスタイルだからこそ、価値が大きいポイントだと感じています。

## まとめ

- TDDが実務で敬遠されるのは工数の問題
- 「AI駆動ならその工数コストが消える」と思っていたが、実際はトークン消費という形に置き換わっただけだった
- それでも使い続けているのは、品質担保と、記憶を持たないAIに実装を任せる上での属人化対策になるから

コストが消えるわけではない、というのが正直な実感ですが、何に対して払っているコストなのかを理解した上で使う分には、十分ペイする投資だと感じています。
