## フォルダごとコピーする、という昔ながらの方法

大きな変更をする前に、とりあえずフォルダごとコピーしておく。自分も昔はよくやっていましたし、たぶん経験がある人も多いと思います。

```text
project
project_backup
project_backup_20260927
```

最初はこのくらいで済んでいても、しばらく続けるとこうなっていきます。

```text
project_old
project_old2
project_最新版
project_最新版2
project_本当に最新版
```

プログラムに限った話でもありません。文書でも同じことが起きます。

```text
企画書.docx
企画書_修正版.docx
企画書_最終版.docx
企画書_最終版2.docx
企画書_本当の最終版.docx
```

「最終版2」の時点で最終じゃないだろ、という話ですが、こういうファイル名には妙なリアリティがあります。

先に断っておくと、これ自体は悪い方法ではありません。変更前の状態を残しておけば、失敗したときに戻せます。ちゃんと役に立つ方法です。問題が出てくるのは、コピーが増えてきてからです。

## どれが本物で、何を変えたのか

しばらく経ってから、こんなフォルダを開いたとします。

```text
project
project_backup_20260920
project_backup_20260925
project_backup_20260927
```

今使っているのはどれでしょうか。日付を見る限り、たぶん一番新しい 9/27 です。ただ、それは「変更してみたけど失敗したので使わなかったもの」かもしれず、実際に使っているのは 9/25 の方かもしれません。フォルダ名からは、どれが採用されたものなのかが分かりません。

もっと困るのが「何を変えたんだっけ？」です。フォルダ同士を比較ツールにかければ差分は分かりますが、分かるのは**何が変わったか**までで、**なぜ変えたのか**は出てきません。数日前なら覚えているかもしれませんが、半年後にはまず覚えていません。

## 状態の保存と、変更履歴の管理は別の話

フォルダのコピーは、その時点の状態を丸ごと残すので、バックアップとしてはちゃんと機能します。ただ、残るのは「その時点の状態」だけで、「いつ・何を・なぜ変更したのか」や「どれが採用されて、どれがボツになったのか」は残りません。

つまり、**状態を保存することと、変更の履歴を管理することは別の話**です。

言い換えると、日付付きのコピーを作ったり、変更前のファイルを別名で残したりするのは、**変更履歴の管理を人間が手作業でやっている状態**です。ファイル名に日付を入れ、どれが最新かを覚えておき、何を変えたかを頭の中で管理する。これをコンピュータにやらせる仕組みが**バージョン管理**です。

バージョン管理では、変更のたびに状態を記録し、そこに「いつ・誰が・なぜ」を添えて、一本の履歴として積み上げていきます。コマンドの話は置いておくとして、イメージとしてはこんなものが残ります。

```text
9/27  検索画面のレイアウトを変更 → 表示崩れが出たので取り消し
9/25  一覧のソート順を登録日順に変更
9/20  初期版
```

これがあれば「今使っているのは 9/25 の変更まで」「9/27 は試して戻した」が一目で分かりますし、必要なら当時との差分を見たり、前の状態に戻したりもできます。フォルダの山からは読み取れなかった情報が、履歴として残るわけです。

## AIにコードを書かせると、この問題はもっと早く来る

最近は、AIにコードを書かせる人も増えてきました。自分も実装のかなりの部分を Claude Code に任せています。

AIは人間より速く、広い範囲を一度に変更します。変更のペースが上がれば、「どれが本物で、何を変えたのか」が分からなくなるまでの時間も短くなります。手作業のコピーで追いかけられる速度ではなくなってくるので、変更履歴の管理は、むしろ今の方が必要性が高いと感じています。

## まとめと、次回予告

- フォルダのコピーは、状態の保存（バックアップ）としては機能する
- ただし「いつ・何を・なぜ変えたのか」「どれが採用されたのか」は残らない
- 状態の保存と変更履歴の管理は別の話で、後者をコンピュータにやらせる仕組みがバージョン管理

今回は、あえて `git init` のようなコマンドは出していません。コマンドを覚える前に、「そもそも何のために使うのか」を押さえておきたかったからです。

とはいえ、バージョン管理 = Git というわけでもありません。自分が最初に触れたバージョン管理システムは Git ではなく、以前の職場で使われていた **Subversion（SVN）** でした。今回の問題自体は、SVN でも解決できます。それでもなぜ自分は Git に移ったのか。次回はその話をします。
