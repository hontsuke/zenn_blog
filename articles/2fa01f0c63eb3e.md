## はじめに

会社の Mattermost に、ちょっとした遊び心で bot を1体飼っています。
見た目はただの「人工無脳」——決まった言葉に反応して、それっぽい返事を返すだけの古典的なやつです。

ただ、中身だけは今どき仕立てで、返答の生成に Gemini を使っています。
「人工無脳のフリした Gemini」という、我ながらちょっと笑えるハイブリッド構成です。

今回はこの遊び半分の bot が、思いのほか個人開発中のサービスの本番機能を助けてくれた、という話を書きます。

## 遊びで作った bot が最初に踏んだ地雷

Gemini の中でも軽量・低コストなモデル（`-flash-lite` 系）を bot の頭脳として使っていたのですが、しばらく運用していると、ある日を境に特定の条件でレスポンスが返ってこなくなる現象に遭遇しました。

原因を追ってみると、モデル名を `-latest` のようなポインタ指定にしていたことが関係していそうでした。ポインタの先が切り替わるタイミングで、挙動が不安定になる瞬間があるようです。

幸い、これは業務のクリティカルパスに乗っていない遊びの bot だったので、実害はほぼゼロ。「へー、こういうこともあるのか」というメモを残して終わりました。

## その学びを、個人開発のサービスに持ち込む

個人で開発・運用している蔵書管理サービス「[本つけ](https://hontsuke.jp/books)」では、書誌データからシリーズ名や巻数を判定する処理に AI を使う計画がありました。書誌 API だけだと、シリーズ名の表記ゆれや巻数の欠落がどうしても残ってしまうためです。

この機能を本番に組み込む段階で、真っ先に頭をよぎったのが Mattermost bot で踏んだ地雷でした。

- モデルのポインタ指定はそのまま使わない
- タイムアウト・リトライを最初から前提にした設計にする
- 万が一レスポンスが得られなかった場合のフォールバックを用意する

という形で、遊びの bot で得た知見を最初から設計に織り込んだ状態でリリースできました。本番で同じ現象にぶつかってから対処するのと、事前に知った上でリリースするのとでは、かかる手間も精神的な負荷もだいぶ違います。

個人開発でよく「遊びのプロジェクトなんて仕事の役に立たない」と言われがちですが、今回は完全に逆でした。実害のない場所で先に転んでおけたのは、割と大きかったです。

## 実装の裏側：設計は Claude.ai、実装は Claude Code

今回の機能に限らず、最近の個人開発は「設計を詰める場所」と「実装する場所」を分けて進めています。

1. Claude.ai とのチャットで仕様や設計判断を詰める
2. 決まった内容を GitLab の Issue にコメントとして残す
3. 実装は Claude Code に渡す

という流れです。GitLab の MCP 連携を使うと、Issue の検索や Merge Request のレビュー・承認・マージまでチャット上から一気通貫でできるので、地味に開発体験が良くなりました。ブランチ運用も develop を統合ブランチにして、Merge Request の説明に `Closes #XX` と書いておけば Issue が自動でクローズされるようにしています。

「設計の意思決定はここでする」「手を動かすのはここに任せる」と役割を分けておくと、後から見返したときに「なぜこの実装にしたか」が Issue のコメントとして残るのも地味に嬉しいポイントです。

## まとめ

- 遊びで作った bot が、本番機能のリスクを先に発見してくれた
- 実害のない場所で失敗しておくのは、地味だけど効く個人開発のコツかもしれない
- 設計は Claude.ai、実装は Claude Code、という分業も併せて紹介した

今後も個人開発（[本つけ](https://hontsuke.jp/books) というマンガ・書籍の蔵書管理サービスを作っています）で得た知見があれば、また記事にしていこうと思います。
