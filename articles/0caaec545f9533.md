## 前置き：市場ではReactが優勢なのは分かってる

先に断っておくと、日本の求人市場を見る限り、フロントエンドの主戦力はReactです。件数ベースで見ても、VueよりReact関連の求人の方が明らかに多く、これは動かしようのない事実だと思っています。

なので、これから書く内容は「Reactは間違っている」という話ではなく、あくまで自分の好みの話です。仕事で必要なら割り切ってReactを使いますが、個人の好みとしてはVue派だし、それには理由があります。今回はその理由を正直に書いてみます。

## 理由1：JSXの記法が肌に合わなかった

一番最初に引っかかったのがJSXでした。HTMLっぽい見た目をしているのに、細部がことごとくJavaScriptの都合に寄せられています。マークアップを書いているはずなのに終始「これはJSなんだぞ」と念押しされ続けている感覚がありました。

比較するとこんな違いがあります。

| 観点 | JSX(React) | テンプレート構文(Vue) |
| --- | --- | --- |
| クラス属性 | `className` | `class` |
| 属性名の表記 | キャメルケース(`onClick`など) | ケバブケース(`@click`など)、HTML標準に近い |
| 条件分岐 | 三項演算子や`&&`をJS式として埋め込む | `v-if` / `v-else` ディレクティブ |
| ループ | `.map()`をJS式として埋め込む | `v-for` ディレクティブ |
| マークアップとロジックの分離 | 同じ関数の中に混在 | `<template>`と`<script>`で分離 |

同じような一覧表示を書くと、見た目にもこれくらいの差が出ます。

```tsx
type Book = {
  id: string
  title: string
}

type BookListProps = {
  books: Book[]
  isLoggedIn: boolean
}

function BookList({ books, isLoggedIn }: BookListProps) {
  return (
    <div className="book-list">
      {isLoggedIn ? <p className="welcome">おかえりなさい</p> : null}
      <ul>
        {books.map((book) => (
          <li key={book.id} onClick={() => console.log(book.title)}>
            {book.title}
          </li>
        ))}
      </ul>
    </div>
  )
}
```

```vue
<script setup lang="ts">
type Book = {
  id: string
  title: string
}

defineProps<{
  books: Book[]
  isLoggedIn: boolean
}>()
</script>

<template>
  <div class="book-list">
    <p v-if="isLoggedIn" class="welcome">おかえりなさい</p>
    <ul>
      <li v-for="book in books" :key="book.id" @click="console.log(book.title)">
        {{ book.title }}
      </li>
    </ul>
  </div>
</template>
```

条件分岐もループも、JSXの方は「JavaScriptの式として」埋め込む一方、Vueの方は「マークアップに付属する属性」として扱われています。この違いが、自分にとっては地味に大きかったです。

Vueのテンプレート構文は、ディレクティブこそあるものの、見た目は最後までHTMLに近い状態を保ちます。マークアップはマークアップとして書けて、ロジックは`<script>`側にきれいに分離される。この線引きの明確さが、自分にとってはかなり心地よいものでした。

JSXの「全部JS」という統一感を評価する人がいるのは理解できますが、自分は「見た目がHTMLならHTMLらしく振る舞ってほしい」というタイプだったようです。

## 理由2：状態管理ライブラリにも癖がある

もう一つが状態管理です。Reactエコシステムの状態管理ライブラリは、Reduxに代表されるように、action・reducer・dispatchといった概念を一通り理解してからでないと、素直に「値を保存して使う」ということができません。

| 観点 | Redux(React) | Pinia(Vue) |
| --- | --- | --- |
| 基本概念 | action・reducer・dispatch | ストア(Composition APIで`ref`/関数を組み合わせる) |
| 値の更新方法 | actionを`dispatch`し、reducerが新しい状態を返す | ストアの値を直接書き換える |
| 変更検知の仕組み | 状態が変わるとコンポーネント関数が再実行される | Proxyベースで変更を自動追跡 |
| 学習コスト | 一連の概念をまとめて理解する必要がある | 「値を触ったら反映される」で直感的に始められる |

単純なカウンターで比べても、経由する概念の数が違います。

```ts
// Redux Toolkit
import { createSlice, configureStore } from '@reduxjs/toolkit'

type CounterState = { value: number }

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 } as CounterState,
  reducers: {
    increment: (state) => { state.value += 1 }
  }
})

export const { increment } = counterSlice.actions
export const store = configureStore({ reducer: { counter: counterSlice.reducer } })
export type RootState = ReturnType<typeof store.getState>
```

```tsx
// コンポーネント側
import { useSelector, useDispatch } from 'react-redux'
import { increment } from './store'
import type { RootState } from './store'

function Counter() {
  const count = useSelector((state: RootState) => state.counter.value)
  const dispatch = useDispatch()
  return <button onClick={() => dispatch(increment())}>{count}</button>
}
```

```ts
// Pinia(Setup Store形式)
import { defineStore } from 'pinia'
import { ref } from 'vue'

export const useCounterStore = defineStore('counter', () => {
  const value = ref(0)
  function increment() {
    value.value += 1
  }
  return { value, increment }
})
```

```vue
<script setup lang="ts">
import { useCounterStore } from './store'
const counter = useCounterStore()
</script>

<template>
  <button @click="counter.increment()">{{ counter.value }}</button>
</template>
```

Reduxの方は「actionを定義して」「dispatchして」「selectorで読む」という一連の作法を踏む必要がありますが、Piniaの方は「ストアの値とメソッドをそのまま呼ぶ」だけで完結しています。関数コンポーネントが再実行されるという設計と密接に絡んでいるので、単純に「状態を置いておきたいだけ」の場面でも、独特の作法に付き合う必要があります。

正直に言うと、自分で手を動かしてReduxを書いていても、途中で「今どのactionがどのstateに効いてるんだっけ」と訳が分からなくなることが何度かありました。仕組みを理解していないわけではないのですが、経由する概念の数が多い分、単純に追いかけるのがしんどい、というのが実感でした。

Piniaはここが対照的です。ストアを定義して、値を直接読み書きするだけで、あとはVueのリアクティビティシステムが勝手に追跡してくれます。「値を触ったら反映される」という素朴な感覚のまま、状態管理まで地続きになっている感じがあります。

## 根っこにあるのは、たぶんWPFの経験

こう振り返ると、自分が求めているのは一貫して「値を触ると、勝手に検知されて反映される」という体験なんだと思います。これは実務で触っていたWPFのデータバインディングの感覚に近いです。プロパティが変わったことを通知すれば、あとは勝手にUIに反映される。Vue・Piniaの「Proxyで変更を追跡する」という仕組みも、根っこにある気持ちよさは同じです。

Reactの「状態が変わったら関数ごと再実行する」という設計は、素直さでいえば別の意味で筋が通っているのですが、自分が慣れ親しんできた「変更を検知して反映する」というモデルとは、そもそも思想が違うものだったんだと思います。

## まとめ

- 市場的にはReactが優勢で、それは理解した上での話
- JSXの「全部JS」という記法より、Vueの「マークアップはマークアップらしく」という線引きの方が肌に合う
- 状態管理も、ReactエコシステムのReduxのような作法より、Piniaの「触ったら反映される」素朴さの方が好み
- 根っこにあるのは、WPFのデータバインディングで馴染んだ「変更検知型」のリアクティビティへの好みだと思う

仕事では引き続き、必要ならReactも割り切って使います。ただ個人開発では、好きな設計思想で作れるという贅沢を、これからも活用していこうと思っています。
