## 名前が似ているから、ややこしい

前回の最後に、GitとGitHubは別のものだ、という話を少しだけしました。

今回は、そこをもう少しちゃんと書いてみます。

Git。

GitHub。

GitLab。

名前に全部「Git」が入っています。

これで別物だと言われても、正直ピンとこないと思います。

GitHubのことを、Gitの公式サイトか何かだと思っている人もいるかもしれません。

名前が似ていなくても、混ざることはあります。

以前の職場で、Gitを使ってもらうためにSourcetreeを教えたことがあります。

Sourcetreeは、Gitを画面で操作するためのアプリです。

ところが、

**Sourcetreeそのものが、Gitだと思っていた人がいました。**

これは、笑う話ではありません。

最初に「Gitを使うためのもの」としてSourcetreeを渡されたら、そう理解しても不思議ではないです。

実際には、ここには三つの別のものが混ざっています。

**Gitは、変更の履歴を管理する仕組み。**

**SourcetreeやVS Codeなどは、Gitを操作するための入口。**

**GitHubやGitLabは、Gitのリポジトリを置いて、共有したりレビューしたりするためのサービス。**

役割がまったく違います。

## Gitだけで、ここまでできる

まず、Gitだけで何ができるのかを見てみます。

GitHubのアカウントは要りません。

インターネットにつながっている必要もありません。

自分のPCにGitが入っていれば、それで始められます。

変更を記録する。

これがコミットです。

記録した履歴を見る。

誰が、いつ、どんなメッセージを付けて変更したのかが分かります。

前の状態と比べる。

どこが変わったのかを、行単位で確認できます。

ブランチを作る。

本線とは別に、試しの変更を進められます。

ブランチをまとめる。

試した変更がうまくいったら、本線に取り込めます。

1話で書いた「どれが本物だ？」という問題も、2話で書いた「中央が死ぬと、なんもできねぇ」という問題も、ここまでの話で片づきます。

**変更履歴の管理そのものは、Gitが一人でやっています。**

GitHubは、この中のどれにも関わっていません。

## Gitを操作する入口は、いろいろある

では、そのGitをどうやって操作するのか。

一番素朴なのは、コマンドです。

`git commit` のような命令を、黒い画面に打ち込む。

Windowsなら、Git Bashを使うこともあります。

でも、入口はそれだけではありません。

- コマンドライン / Git Bash
- Sourcetree
- TortoiseGit
- VS Code
- Visual Studio
- Eclipse

どれも、Gitを操作するための入口です。

最近なら、AIに「コミットしておいて」と頼む、という入口もあります。

見た目も操作方法もバラバラです。

でも、どの入口から触っても、扱っているのは同じGitのリポジトリです。

Sourcetreeでコミットしても、VS Codeでコミットしても、コマンドでコミットしても、残る履歴は同じ。

**入口が違うだけで、Gitは一つです。**

だから、Sourcetreeを使うのをやめても、履歴が消えるわけではありません。

冒頭の「SourcetreeがGitだと思っていた」という話も、ここを分けて考えるとすっきりします。

## リモートは、GitHubじゃなくてもいい

じゃあ、みんなで共有するときはGitHubが必要なのか。

そうでもありません。

Gitには「リモート」という考え方があります。

名前だけ聞くと、どこか遠くのサーバーのことに思えますが、中身は単純です。

**自分の手元とは別の場所にある、もう一つのリポジトリ。**

それだけです。

その「別の場所」は、GitHubでもいいし、GitLabでもいい。

社内のファイルサーバーでもいい。

極端な話、USBメモリでもかまいません。

たとえば、共有フォルダにあるリポジトリを取ってくるなら、

```bash
git clone //fileserver/share/project.git
```

のように、場所を指定するだけです。

前回、「社内のファイルサーバーにGitのリポジトリを置いて使うこともありました」と書いたのは、こういう使い方のことです。

GitHubがなくても、Gitは共有できます。

それに、リモートは一つとは限りません。

Gitは「分散型」のバージョン管理システムです。

前回、Gitでは自分のPCにもリポジトリがある、と書きました。

SVNのように、中央のリポジトリが一つあって、そこにみんながつながる、という形ではありません。

自分の手元のリポジトリも、GitHubにあるリポジトリも、それぞれが一人前のリポジトリです。

だから、一つのリポジトリに、リモートをいくつも登録できます。

たとえば、

```text
origin   → GitHub
gitlab   → GitLab
internal → 社内のGitサーバー
```

のような構成も、普通にできます。

よく見かける `origin` という名前も、特別な接続先というわけではありません。

最初に登録したリモートに付けられることが多い、ただの慣例的な名前です。

つまり、

**Gitのリポジトリと、GitHubやGitLab上の置き場所は、一対一で結びついているわけではありません。**

置き場所は、あとから増やすことも、変えることもできます。

## そもそも、Gitの方が先にあった

順番の話をしておくと、

**Gitが生まれたのは2005年。**

**GitHubができたのは2008年です。**

GitはもともとLinuxの開発のために作られました。

Linuxの開発では、変更をメールでやり取りする文化があり、今でもその流れが残っています。

つまり、GitHubが生まれる前から、Gitは普通に使われていました。

GitHubは、Gitを使うための便利な場所として後から出てきたものです。

## じゃあ、GitHubは何をしているのか

では、GitHubやGitLabは何をしてくれているのか。

ざっくり言うと、Gitの周りにあると便利なものを揃えてくれています。

**リポジトリを置いておく場所。**

サーバーを自分で用意しなくても、リポジトリを共有できます。

**ブラウザで見られる画面。**

コマンドを打たなくても、ファイルや履歴や差分を見られます。

**Issue。**

やることや不具合を書いておく場所です。

**プルリクエスト（GitLabではマージリクエスト）。**

「この変更を取り込んでください」とお願いして、レビューしてもらう仕組みです。

**CI/CD。**

変更を送ったら、自動でテストを流したり、デプロイしたりする仕組みです。

ここで一つ、意外に思われるかもしれないことがあります。

**IssueもプルリクエストもCI/CDも、Gitの機能ではありません。**

GitHubやGitLabが、Gitの外側に作ったものです。

だから、GitHubとGitLabで呼び方が違ったり、使い勝手が違ったりします。

Git本体には、Issueという考え方そのものがありません。

## 混ざって見える理由

それでも「Gitを使う＝GitHubを使う」と思われやすいのには、理由があると思います。

まず、名前が似ている。

次に、Gitの入門記事の多くが、GitHubのアカウントを作るところから始まる。

そして、普段目にするGitの操作が、GitHubの画面の上で行われていることが多い。

プルリクエストをマージするボタンを押していると、それがGitの機能のように見えてきます。

最近だと、AIの開発ツールもGitHubとつながることを前提にしているものが多いです。

こうなると、GitとGitHubを分けて考える機会は、ますます減っていきます。

別に、それで困ることはあまりありません。

ただ、何かうまくいかなかったときに、

**それはGitの問題なのか、GitHubの問題なのか。**

これが分かるだけで、調べる場所がかなり絞れます。

## 自分はGitLabだった

ちなみに、自分が長く使っていたのはGitHubではなく、GitLabでした。

それも、自分でサーバーに立てて使っていました。

なぜGitLabだったのかは、それはそれで長い話になるので、別の機会に書こうと思います。

ここで言いたいのは、

**GitHubでもGitLabでも、中で動いているのは同じGitだ**

ということです。

GitHubからGitLabに移っても、GitLabからGitHubに移っても、Gitの使い方そのものは変わりません。

リポジトリを移すときも、履歴を作り直す必要はありません。

新しい置き場所をリモートとして登録して、そこへpushすれば、それまでの履歴ごと移せます。

ただし、IssueやプルリクエストはGitの外側の機能なので、pushしても一緒には移りません。

コミットはコミットで、ブランチはブランチです。

## 次は、ブランチの話

ここまでで、Gitそのものは一人でもかなりのことができる、という話をしてきました。

その中で、何度か「ブランチ」という言葉が出てきました。

前回も、Gitで初めてブランチを切り替えたとき「え、これでいいの？」と思った、と書きました。

でも、そもそもブランチはなぜ必要なのか。

一人で作業しているなら、本線だけで十分じゃないのか。

ブランチは、文字だけで説明されても、なかなかイメージしにくいものです。

SourcetreeのようなGUIや、GitLabの画面では、ブランチがどこから分かれて、どこで戻ってきたのかを、図で見ることができます。

**Gitを理解するには、画面で見た方が分かりやすいものもあります。**

特に、ブランチはそうです。
