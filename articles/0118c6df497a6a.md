## 要らないと書いたのに、課金した

以前、[Claude Code + Codexは個人開発の規模だと要らなかった](https://zenn.dev/hontsuke/articles/c2038913b11f84)という記事を書きました。

にもかかわらず、ChatGPT Plusに課金しました。

### 課金した理由

理由はシンプルで、Claude Codeのトークンが足りないからです。個人開発している蔵書管理サービス「[本つけ](https://hontsuke.jp/)」の開発で、Claude Codeをがっつり使っています。このままClaudeのプランを上げて重課金するよりは、本つけ以外の作業をCodexに任せて、OpenAIに課金するほうがいいか、と考えました。

前回はレビュー役として組み合わせる話でしたが、今回は作業の分担です。そうして実際に使い分けてみると、比べるつもりはなかったのに、違いがいろいろ見えてきました。

### 先に結論

先に結論を書くと、一番気になったのは「どっちが賢いか」ではありませんでした。

**相談と作業が、どれだけ地続きになっているか。**

これが思っていた以上に大きな差でした。

:::message
この記事は、2026年9月時点で筆者が実際に両方を使ってみた結果です。機能の網羅的な比較ではないので、「この設定ならCodexでもできるよ」といった情報があれば、ぜひコメントで教えてください。
:::

## ChatGPTで相談して、Codexに作業させる

ちょうど[note](https://note.com/hontsuke_jp)で新しい連載を始めようとしていたので、こちらをChatGPTとCodexの担当にしました。構成はこうです。

- ChatGPT：企画や方向性の相談
- Codex：記事ファイルの作成・修正
- Git：成果物の管理

役割分担としてはきれいですし、最初はいい構成に思えました。

## ChatGPTで話したことを、Codexは知らない

### 「さっきの話」がない

当たり前といえば当たり前ですが、ChatGPTで延々と相談した内容を、Codexが知っているわけではありません。

ChatGPTとの会話では、「この連載はプログラミング入門じゃないよね」「そもそもアプリを作る必要すらないのでは」「解決方法そのものをAIに考えさせればいいのでは」と、企画の方向性が少しずつ変わっていきます。人間同士の編集会議なら「さっきの話を踏まえて」で済みますが、Codexに作業を頼むと、その「さっきの話」がありません。

### GitHubコネクタは読み取り専用だった

最初は、ChatGPTでの会話の内容をそのままCodexに渡そうとしました。ところが、ChatGPTにもGitHubのコネクタはあるものの、自分が使った範囲では読み取り専用でした。リポジトリを読むことはできても、会話で決まったことをIssueやファイルに書き出すことはできません。結局、人間がコピーして運ぶことになりました。

### PROJECT.mdとCONTEXT.mdで教育する

そこで、プロジェクトの方針を `PROJECT.md` に書くことにしました。

ところがしばらくすると、今度は「なぜその方針になったのか」が抜けていることに気づきます。連載を書いていると、この「なぜ」が意外と重要でした。そこで `CONTEXT.md` も作りました。PROJECT.mdが現在のルール、CONTEXT.mdがそこに至った経緯です。

これはかなり効きました。試しに「Todoアプリの記事を書いたらどう？」と聞いてみると、

> 普通のTodoアプリを作る記事では、この連載の方向性には合いにくい。ただし、実際の困りごとから考えた結果Todoアプリに行き着くなら合う

という趣旨の答えが返ってきました。ちゃんと教育できています。よしよし、と思いました。

## あれ？ 何やってるんだ？

改めて流れを書き出すと、こうなっていました。

1. ChatGPTで相談する
2. 重要なことが決まる
3. PROJECT.mdやCONTEXT.mdに反映する
4. Codexに読ませて作業させる
5. その結果をまたChatGPTに持っていく

あるとき気づきました。

**俺、AI同士の伝書鳩やってない？**

AIで仕事を楽にするはずだったのに、「ChatGPTさんからのお手紙です」とCodexへ運び、「Codexさんから返事が来ました」とChatGPTへ運んでいる。しかも両方ともかなり賢い。賢いAI二人の間を、人間が走り回っています。

## それ、使い方の問題では？

ここは正直に書いておくべきところで、これはツールの性能差というより、使い方が生んだ構造でもあります。Claudeでも、claude.aiの普通のチャットで相談した内容をClaude Codeが自動的に知っているわけではありません。逆に、最初からCodexの中で相談も作業も済ませれば、伝書鳩にはなりにくいはずです。

ただ、ChatGPTは「相談する場所」、Codexは「作業する場所」と、入口が最初から分かれています。普段チャットしている画面と、作業させる画面が別物なので、自然と相談はChatGPT、作業はCodex、という分け方になっていました。

## Claude Codeでは、同じ画面の中で完結した

ここでClaude Codeとの違いがはっきりしました。

### Remote Controlで、同じ画面に並ぶ

自分の場合、Claude CodeのRemote Controlを使うと、手元のPCで動いているClaude Codeのセッションが、claude.aiの画面にそのまま並びます。普段claude.aiで使っているチャットの一覧の中に、作業中のセッションが1つのチャットとして出てくる感覚です。

つまり、**普段相談している画面の中に、ファイルを触っている相手がいます**。別のアプリに切り替えて、方針を書いたファイルを渡して……という中継がそもそも発生しません。

厳密には、claude.aiの他のチャットとClaude Codeのセッションが記憶を共有しているわけではないと思います。それでも同じ画面の中で、相談の延長として作業を頼めるので、体感としては情報が共有されているように見えます。この「見え方」が、思っていた以上に効いていました。

実際、この記事の推敲も「リモート繋がってる？」と確認するところから始まっています（デスクトップアプリからは繋がらず、Web画面から繋いだのはご愛嬌）。

### コネクタで、リポジトリに書き込める

もうひとつ大きかったのが、claude.aiのコネクタ（リモートMCP）です。ChatGPTのGitHubコネクタと違って書き込みまでできるので、GitHubやGitLabに繋いでおくと、チャットで決まった方針を、チャットの中からそのままIssueやリポジトリに書き込めました。Claude Codeは、それを読んで作業すればいい。

ChatGPTとCodexの組み合わせでは人間が運んでいた「さっきの話」が、Claudeではリポジトリ経由で渡せました。伝書鳩の役を、GitHubやGitLabが代わりにやってくれるわけです。

Codexでも、設定や使い方次第で同じような流れは作れるのかもしれません。ただ、今回の自分の使い方では、そこまで辿り着けませんでした。

もちろんClaude Codeにもコンテキストの限界はありますし、何でも覚えているわけではありません。それでも体感として、**「相談するAI」と「作業するAI」が分かれている感じが薄い**。使い方の問題だとしても、その使い方が自然にできる仕組みがあるかどうかは、ツールの差だと思います。

### 地続きの裏返し：勝手に進む

ただ、地続きなのはいいことばかりではありません。相談と実務が直結しているので、「今は相談だけ」「ここから先は自分でやる」といった分担をきちんと伝えておかないと、相談している最中にもどんどん先に進んで、ファイルを書き換えてしまいます。伝書鳩はいらなくなったものの、今度は「ちょっと待って」と止める役が必要になりました（笑）。

### 対策：CLAUDE.mdにルールを一言

これは、ルールを一言入れておくだけでかなり落ち着きます。Superpowersのbrainstormingのような仕組みもありますが、自分はプロジェクトのCLAUDE.mdにこう書きました。

```markdown
## 作業の進め方
- 相談・壁打ちの段階ではファイルを編集しない。案は会話の中で示す
- ファイルを書き換えるのは、明示的に頼まれたとき、または確認を取ってから
```

これで、相談中はチャットらしく案を出すだけにとどまり、作業は頼んだときに始まるようになります。

## もうひとつの差：作業中が見えるか

### まず、遅い

別の場面で、CodexにIssueの後処理程度の作業をさせたときには、正直かなり遅いと感じました。時間を測ったわけではありませんが、遅いのは確かです。

### 途中経過が見えるか

そのうえで、もうひとつ気になったのが、自分が使った画面では**作業中に何をしているのかが見えにくかった**ことです。

Claude Codeでは、どのファイルを読んでいるか、何を検索しているか、どこを編集しているか、テストが失敗してやり直しているか、がリアルタイムに見えます。なので途中で「そっちじゃない」「そこは調べなくていい」と割り込んで軌道修正することがよくあります。これは単なる進捗表示の違いではなく、**人間が作業途中に介入できるかどうか**の違いです。

一方でClaude Codeには逆の問題もあって、状況が見えるぶん、放っておけばいいのについ眺めてしまいます。

Codexはむしろ、「仕事を渡す → 別のことをする → 終わったら戻る」という委託型の使い方を想定しているのかもしれません（ただ、実際には後述のとおり、まだやり取りが多めでした）。

### 比べるとこんな感じ

今のところの印象を整理すると、こうです。

| | Claude Code | Codex |
|---|---|---|
| 途中経過 | 見える | 見えにくい |
| 途中での介入 | しやすい | しにくい |
| 人間側 | つい眺めてしまう | 別の作業ができる |

遅いうえに途中が見えないので、画面の前で待っていると余計に長く感じます。このあたりは、もう少し規模の大きい作業を任せてみないと分からないので、結論ではなく観察として置いておきます。

## Codexがダメだったわけではない

誤解のないように書いておくと、Codex自体はちゃんと仕事をします。リポジトリを読ませれば理解しますし、PROJECT.mdやCONTEXT.mdを用意したあとは、かなりこちらの意図に沿った判断もするようになりました。

ただ、使っていて受ける印象は、ひと昔前のAIに近いものでした。ある程度はやってくれるものの、チャットで何度もやり取りしながら進める感覚がまだ色濃く残っています。まとめて任せて、あとは自分で進めてもらう、というところまではいきませんでした。

今回分かったのは、**Codex単体の性能とは別のところに、自分の働き方との相性があった**ということです。

## 引き継ぎ書が増えていく

PROJECT.md、CONTEXT.md、次はROADMAP。AIに仕事を引き継ぐための文書が、だんだん充実してきました。

これはこれで、プロジェクト管理としては悪くありません。人間のチームでも、仕様や意思決定の経緯を残すのは大切です。

でも今回やりたかったのは、**AIチームのマネージャーになることではなく、記事を書くこと**でした。

## モデルの賢さだけ見ても分からない

AIコーディングツールを比べるとき、ついコード生成能力やバグ修正能力、速度、トークン消費といったモデル寄りの指標を見たくなります。もちろんそれも大事です。

ただ、どちらも十分賢いなら、「IQが3高いAI」より「話が通じたまま仕事を続けられるAI」のほうが楽です。実際のプロジェクトで効いてくるのは、

- どこで相談するのか
- どこで作業するのか
- プロジェクトの文脈はどこにあるのか
- その文脈を、誰が次のAIへ渡すのか

といった、働き方の部分でした。ツールによって、人間側の仕事の仕方そのものが変わる。これはモデルのベンチマークには出てこない比較軸だと思います。

## おわりに

ChatGPT Plusに課金して、Codexを使ってみて、PROJECT.mdとCONTEXT.mdを作って、AIへの引き継ぎ方法まで考えました。

Codexはちゃんと仕事をしました。ChatGPTもちゃんと相談に乗ってくれました。問題は、その二人の間にいました。

**俺です。**

来月も課金を続けるかは、もう少し使ってから考えることにします。たぶん。
