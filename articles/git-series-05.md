## この連載を書いていて、途中で気づいた

このGit連載を書いている途中で、気づきました。

**「あれ。これ、マージしたら公開されるんじゃね？」**

一人で書いている記事です。

なのに、作業ブランチがあり、レビューがあり、マージ先を分ける必要まで出てきました。

なぜこんなことになったのか。

理由は簡単です。

**一人で作っているのに、変更するのが一人ではなくなったからです。**

## 最初は、もっと単純に考えていた

この連載の記事は、GitHubのリポジトリで管理しています。

記事を書く。

ブランチを作る。

プルリクエストを作る。

レビューする。

問題なければマージする。

これだけなら、普通です。

ただし、このリポジトリには一つ事情があります。

Zennと連携していて、`main` に入った記事はZennに取り込まれます。

記事に「公開する」という設定が入っていれば、そのまま公開されます。

つまり、`main` に入ったものは、単なる「完成した原稿」ではありません。

公開につながる側です。

つまり、

**mainへのマージは、ただのファイル整理ではない。**

その先に公開があります。

記事を書いているだけなら、それほど問題にはならなかったかもしれません。

ところが今回は、AIをかなり使っています。

## 一人で書いている。でも、一人では作っていない

この連載では、自分一人だけが文章を触っているわけではありません。

まず、自分が考えます。

ChatGPTと相談します。

叩き台を作ります。

Claudeに渡します。

ClaudeがGitHub側の記事を修正します。

プルリクエストを作ります。

それをまた自分とChatGPTで読みます。

修正点があればClaudeへ戻します。

```text
自分
 ↓
ChatGPT
 ↓
自分
 ↓
Claude
 ↓
GitHub
 ↓
自分
 ↓
ChatGPT
 ↓
自分
 ↓
Claude
```

AI同士を連携させたかったはずなのに、

**なぜか途中にずっと自分がいます。**

理由は単純で、ChatGPTはGitHubのリポジトリを読めても、書き込めないからです。

やらせたいのに、できない。

逆にGitLabの方では、ChatGPTからmainへのコミットまでできてしまいました。

できるのに、やらせたくない。

これは別の問題として、そのうち何とかしたいところです。

ただ、もっと重要なのは、

**変更する主体が増えている**

ということです。

昔なら、

「一人で作っているんだから、自分しか変更しない」

で済みました。

今は違います。

自分が変更する。

Claudeが変更する。

別のAIがレビューする。

場合によっては、そのAIもリポジトリを操作できる。

一人開発なのに、状況だけを見ると、だんだんチーム開発に似てきます。

## 「できる」と「やっていい」は別だった

AIにリポジトリを接続すると、できることが増えます。

ファイルを読む。

変更する。

コミットする。

プルリクエストを作る。

環境によっては、さらにその先まで操作できます。

これは便利です。

人間が、

「このファイルを開いて」

「ここを書き換えて」

「コミットして」

と一つずつ操作しなくてもいい。

AIに、

> この内容で修正して、コミットしておいて。

と頼めば済みます。

ところが、できるようになると次の問題が出ます。

**どこまでやらせていいのか。**

技術的にmainへ書ける。

だからmainへ書かせる。

技術的にマージできる。

だからマージさせる。

技術的に公開まで進められる。

だから全部任せる。

これは、少し違います。

**できることと、やっていいことは別です。**

## mainって、何だろう

ここで、前回までの話に戻ります。

ブランチを使う理由は、

**今の正しい状態と、これから行う変更を分けるため**

でした。

では、今回の `main` は何でしょう。

単に最新のファイルが入っている場所でしょうか。

作業中のものを置いてもいい場所でしょうか。

レビュー前のものを入れてもいいのでしょうか。

AIが「完成しました」と判断したら入れていいのでしょうか。

今回、自分が欲しかったのは、

**「ここにあるものは公開していい」**

と言える場所でした。

そう考えると、mainの意味がかなりはっきりします。

mainは、

**最後に人間が「ここまでOK」と判断した状態**

にしておきたい。

少なくとも、この連載ではそう考えました。

## すると、一段足りなかった

最初は、

```text
作業ブランチ
     ↓
     PR
     ↓
   main
```

くらいで考えていました。

普通に見えます。

でも、今回のmainは公開につながっています。

記事を書いた。

AIに直してもらった。

PRを作った。

ちょっとレビューした。

マージ。

公開。

これは怖い。

それに、連載として出すなら、最後にまとめてやりたいこともありました。

シリーズ名を入れる。前後の話へのリンクを張る。公開日を1日ずつずらす。

全部の話が揃ってから、まとめて仕上げたい。

そこで、途中に一段欲しくなりました。

```text
作業ブランチ
     ↓
     PR
     ↓
 中間ブランチ
     ↓
 最終確認
     ↓
   main
     ↓
   公開
```

作業が終わったことと、

公開していいことを、

分けたかったのです。

前回の話と同じです。

**状態を分けたいから、ブランチを分ける。**

## Git Flowを使おう、と思ったわけではない

ここで「Git Flow」という言葉が出てきます。

Git Flowには、役割ごとにブランチを分ける考え方があります。

`main`

`develop`

`feature`

`release`

`hotfix`

などです。

詳しい使い方は、ここでは説明しません。

この記事で言いたいのは、

「Git Flowではこのブランチ名を使いましょう」

という話ではないからです。

自分も今回、

**「よし、Git Flowを導入しよう」**

と考えて始めたわけではありません。

AIを使いながら実際に作業していたら、

「ここはまだ作業中」

「ここはレビュー済み」

「ここから先は公開していい」

という状態を分けたくなった。

その結果、

**Git Flowが解決しようとしていた問題に、自分でもう一度ぶつかった。**

そんな感覚の方が近いです。

## 昔は「人」を分けていた

チーム開発でブランチが必要になる理由は分かりやすいです。

Aさんが新機能を作る。

Bさんがバグを直す。

Cさんがリリース準備をする。

それぞれが同時に作業します。

だから変更を分けます。

昔なら、

```text
人A → feature-A
人B → feature-B
人C → release
```

というイメージでした。

でも今は、

```text
自分   → 変更
AIその1 → 変更
AIその2 → レビュー
AIその3 → 別の変更
```

ということが普通に起こり始めています。

もちろん、AIは人間の開発者と同じではありません。

責任を取るわけでもありません。

自分で「これは公開してよい」と責任を持って判断してくれるわけでもありません。

だからこそ、

**誰が、どの状態まで変更していいのか**

を考える必要があります。

## AIに任せるほど、境界が必要になる

AIを使う目的は、人間が全部手で操作しなくて済むようにすることです。

自分も、Gitの細かいコマンドまで毎回打ちたいわけではありません。

ブランチを作る。

コミットする。

必要な変更を別のブランチへ持っていく。

そういう操作は、どんどんAIに任せればいいと思っています。

でも、操作を任せるほど、

**どこまで任せるのか**

を決める必要が出てきます。

たとえば、

「作業ブランチの中なら自由に直していい」

「PRまでは作っていい」

「中間ブランチへの反映はレビュー後」

「mainへ入れるのは最終確認後」

というようにです。

これはAIを信用する、信用しないという話だけではありません。

人間同士の開発でも同じです。

間違いは起きます。

勘違いも起きます。

指示した側が間違っていることだってあります。

だから、

**間違えても壊れにくい場所で作業する。**

Gitのブランチは、そのためにも使えます。

## 「できるけど、やらせない」

AIに権限を与えれば、できることは増えます。

全部自動化できた方が便利に見えます。

でも、自動化できる場所を全部自動化する必要はありません。

自分は今、

**「できるけど、やらせない」**

という境界も大事だと思っています。

AIには作業を任せる。

コミットも任せる。

PR作成も任せる。

レビューにも使う。

でも、

「これは完成なのか」

「これは公開していいのか」

という境界は残す。

その境界を、GitのブランチやPRで形にしておく。

すると、

人間が毎回すべての操作をする必要はないけれど、

最後の判断まで知らないうちに通過してしまうことも防げます。

## 一人開発が、小さなチーム開発になった

Gitを使い始めた頃、

ブランチはチーム開発のためのもの、という印象がありました。

複数人が同時に作業するから必要になる。

もちろん、それは今でも正しいです。

でもAIを使うようになって、少し見え方が変わりました。

ブランチが分けていたのは、人ではなく、変更の状態だったのかもしれません。

作業中なのか。レビュー済みなのか。公開していいのか。

作る人が一人でも、変更する主体が増えれば、その状態を分ける必要が出てきます。

そうなると、一人開発でも、

**小さなチーム開発のような変更管理**

が必要になります。

だから、昔からあるGitの仕組みが、むしろAI時代になって便利になってきました。

## Gitを覚える意味も、少し変わった

この連載の最初に、

「最新版」フォルダが増えていく話を書きました。

変更履歴を人間がフォルダ名で管理していたわけです。

そこからSVNの話をして、

Gitへ移った話をして、

GitとGitHubやGitLabは別物だという話をして、

ブランチの話をしました。

ここまで来ると、自分がGitで大事だと思っていることも、かなりはっきりします。

前回も書きましたが、Gitのコマンドを全部覚えることではありません。

AIがいる今なら、コマンドは聞けばいい。

操作そのものを任せてもいい。

それより大事なのは、

**今、何が正しい状態なのか。**

**これから何を変更したいのか。**

**その変更を、どこまで進めていいのか。**

それを人間が分かっていることです。

## AIにGitを使わせるために、人間がGitを理解する

少し変な話です。

AIがGitを操作してくれるなら、人間はGitを知らなくてもよさそうです。

でも実際に使ってみると、逆でした。

AIにGitを使わせるからこそ、

人間側が、

「この変更は、AIに任せていい」

「ここから先は、自分が見てから」

「ここから先は公開につながる」

と判断できる必要があります。

コマンドを打つ役目はAIに渡せます。

でも、

**どういう状態にしたいのかを決める役目までは、渡せません。**

少なくとも、自分は今のところ渡したくありません。

## 結局、Gitは変更を管理する道具だった

最初の記事で書いた話に戻ります。

Gitは、単なるバックアップではありません。

GitHubを使うためだけの道具でもありません。

ファイルを保存するだけの仕組みでもありません。

**変更を管理するための仕組みです。**

そしてAIがコードや文章を変更するようになった今、

管理しなければならない「変更」は減るどころか増えています。

誰が変更したのか。

何のための変更なのか。

どこまで確認されたのか。

どの状態を正しいものとするのか。

AIがそこに加わっても、この問題はなくなりません。

むしろ、前よりはっきり見えるようになりました。

自分が昔、Gitを使い始めたときには、

まさかAIにGitを操作させることになるとは思っていませんでした。

でも、やっていることの根っこは同じです。

**今の正しい状態を残しながら、次の変更を安全に進める。**

そのためにGitを使う。

AI時代になっても、そこは変わらないようです。
